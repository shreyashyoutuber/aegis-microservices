# AEGIS - Distributed Emergency Response Engine

**AEGIS** (meaning "Shield" or "Protection") is an enterprise-grade, distributed Microservices backend designed to handle large-scale emergencies like floods, earthquakes, and fires.

## The Problem It Solves
When a major disaster strikes, thousands of panicked people try to call for help or use an app at the exact same time. A traditional "monolithic" server will instantly crash under this heavy load, leaving people without help when they need it most. 

Furthermore, dispatchers matching victims to ambulances or boats manually is too slow.

## The AEGIS Solution (How it handles heavy conditions)
AEGIS is built using a **Microservices Architecture**. Instead of one giant application, the system is broken down into small, independent pieces. 

If 10,000 people report a flood simultaneously, only the **Incident Service** gets heavy traffic. The system (via load balancers) will automatically create 10 identical copies of the Incident Service to handle the load without crashing, while the rest of the system remains perfectly normal.

## 100% Completed Backend Microservices

We have successfully built and verified the entire backend engine consisting of the following components:

### 1. Eureka Server (Port 2026) - *The Phonebook*
* **What it is:** The Service Registry.
* **Its Job:** Every time a microservice boots up, it registers itself here. This allows services to find each other dynamically without hardcoding IP addresses, which is crucial when the system auto-scales up or down.

### 2. API Gateway (Port 8080) - *The Traffic Cop*
* **What it is:** The Single Entry Point for the entire system.
* **Its Job:** The frontend (or mobile app) only ever talks to Port 8080. The Gateway looks at the request (e.g., `/incidents`) and seamlessly routes it to the correct backend service.

### 3. Auth Service (Port 8085) - *The Bouncer*
* **What it is:** Security and Identity Management.
* **Its Job:** Handles user registration and login. It uses **BCrypt** to encrypt passwords and issues **JWT (JSON Web Tokens)**. This ensures that the system is entirely stateless—no sessions are stored in memory, making it lightning fast and highly secure.

### 4. Incident Service (Port 8081) - *The Panic Room*
* **What it is:** Emergency Data Management.
* **Its Job:** Receives, logs, and manages emergency reports (Floods, Fires, etc.) including their exact GPS locations and severity.

### 5. Resource Service (Port 8082) - *The Armory*
* **What it is:** Rescue Asset Management.
* **Its Job:** Keeps a live inventory of all rescue units (Ambulances, NDRF Boats, Fire Trucks) and tracks whether they are `AVAILABLE`, `DEPLOYED`, or in `MAINTENANCE`. It also stores alternative contact methods (like VHF Radio frequencies or Satellite IDs) in case cellular networks fail.

### 6. Response Service (Port 8083) - *The Brain*
* **What it is:** The Automated Dispatch Engine.
* **Its Job:** This service uses **Spring Cloud OpenFeign** to talk to both the Incident and Resource services internally. When an emergency is confirmed, the Response Service automatically finds the nearest `AVAILABLE` rescue unit, changes its status to `DEPLOYED`, and creates a permanent dispatch record.

## What Happens When Devices Fail? (The Fallback Plan)
AEGIS is a **decision-support engine**. It figures out *who* to send and *where* to send them.

If a disaster destroys all cell towers and internet:
1. The backend server runs in a secure, powered control room.
2. The Dispatcher looks at the AEGIS dashboard (which is still running on the local network).
3. The Dispatcher reads the system's dispatch recommendation.
4. The Dispatcher uses **VHF/UHF Radio**, **Satellite Messengers**, or even **Physical Runners** to deliver the instructions to the rescue boats.

The knowledge and matching logic generated by AEGIS is never lost, regardless of how harsh the physical conditions become.
